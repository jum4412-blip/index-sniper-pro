# BTC·ETH Trend Core v1.0.0-rc1

Bitget UTA의 BTCUSDT·ETHUSDT USDT 무기한 선물용 프로그램입니다. `etc`는 앞선 대화의 ETH(이더리움)로 해석했습니다. ETC(이더리움 클래식)는 거래하지 않습니다.

**실주문 기능을 구현한 후보 버전입니다. 수익성이 검증된 상품이나 원금 보장 프로그램이 아닙니다.** 오프라인 실행 검사는 전략의 수익성 검증을 대신하지 않습니다. 이 파일을 받는 것만으로 서버가 바뀌거나 거래가 시작되지는 않습니다.

기존 `index-sniper-pro`의 전략 코드를 덮어쓰지 않는 별도 설치입니다. Python 3.10 이상, Ubuntu/Linux에서 동작하며 외부 pip 패키지는 필요하지 않습니다. 기존 서버의 `.env`를 로컬에서 읽습니다. SSH 키나 API 키는 이 ZIP에 포함하지 않았습니다.

## 설정과 의미

| 항목 | 기본값 | 의미 |
|---|---:|---|
| 거래 대상 | BTCUSDT, ETHUSDT | 다른 종목은 진입하지 않음 |
| 레버리지 / 증거금 방식 | 5배 / 교차 | 기존 UTA 교차 방식을 유지. 잔고 전체의 5배를 매수하는 설정이 아님 |
| 동시 포지션 | 전체 합계 1개 | BTC와 ETH를 동시에 보유하지 않음 |
| 한 거래 계획 위험 | 현재 계좌 평가잔고의 0.5% 이내 | 최초 손절 거리, 왕복 수수료 예산, 불리한 체결 예산으로 수량 계산 |
| 추정 초기 증거금 상한 | 평가잔고의 30% | 위험 기준으로 계산한 수량이 먼저 적용되므로 보통 이보다 작음 |
| 일간 손실 한도 | 2% | 신규 진입 차단, 보유 중이면 해당 봇 포지션의 청산 시도 |
| 주간 손실 한도 | 4% | 동일. UTC 달력 기준 |
| 최고 평가잔고 대비 하락 한도 | 8% | 지속 중지 상태로 전환. 재시작으로 해제되지 않음 |
| 연속 순손실 | 3회 후 24시간 대기 | 수수료·펀딩비를 포함한 거래소 순손익 기준 |
| 청산 후 대기 | 최소 4시간 | 두 종목 전체에 적용 |
| 추가 매수 / 물타기 / 마틴게일 | 없음 | 기존 포지션에 수량을 더하지 않음 |

첨부 기록의 약 1,018 USDT를 예로 들면 0.5%는 약 5.09 USDT입니다. **실주문은 과거 기록의 1,018을 고정 사용하지 않고 거래소에서 읽은 현재 잔고를 사용합니다.** `paper_seed=1018`은 모의 운용에만 쓰입니다.

0.5%는 손실의 보장 상한이 아닙니다. 급격한 가격 이동, 거래소/API 장애, 예상보다 나쁜 청산 체결, 계속 누적되는 펀딩비 때문에 초과할 수 있습니다. 교차 증거금은 포지션 증거금 30%만 위험에 노출되는 구조가 아닙니다. 계좌의 다른 잔고도 손실 흡수에 쓰일 수 있습니다.

일간·주간 한도는 프로그램이 관측한 계좌 평가금액으로 판단합니다. 일/주가 바뀐 뒤 처음 정상 조회한 금액이 새 기준입니다. 정확한 한도 가격에서 체결된다는 보장은 없습니다. 기존 Larry의 당일·주간 기준, 최고 잔고, 연속 손실, 대기 시간과 중지 사유를 가능한 경우 같은 계좌임을 확인하고 가져옵니다. 설치 당일에 이미 한도를 넘었다면 신규 진입하지 않는 것이 정상입니다.

## 진입 근거

1. **큰 방향은 완료된 일봉으로 판단합니다.** 종가 > EMA20 > EMA60이면 롱만 검토하고, 종가 < EMA20 < EMA60이면 숏만 검토합니다. 그 외에는 관망합니다. EMA는 방향 필터이며 미래 상승·하락 확률이 아닙니다.
2. **진입은 완료된 4시간봉의 새로운 20봉 채널 돌파입니다.** 직전 20개 봉의 고점보다 위에서 마감한 새로운 돌파에 롱을 검토합니다. 숏은 반대입니다. 돌파 계산에서 신호 봉 자체는 제외합니다. 이미 이전 봉에서 돌파한 상태를 매번 신규 신호로 세지 않습니다.
3. 신호 봉 마감 후 5초부터 15분 사이에만 시도합니다. 같은 종목·봉·방향의 신호는 한 번만 소비합니다. 주문이 미체결돼도 같은 신호로 재주문하지 않습니다. 두 종목 신호가 동시에 나오면 BTC를 먼저 검토하는 고정 순서이며, 사후 수익으로 순서를 바꾸지 않습니다.
4. 현재 호가에서 돌파가 유지되고, 신호 종가에서 0.5 ATR 이상 멀어지지 않았을 때만 접근합니다. 넓은 스프레드, 마크/지수 가격 괴리, 불리한 높은 펀딩비, 손절 대비 큰 비용, 거래소 최소 주문 미달이면 건너뜁니다.
5. 최대 5bp 불리한 가격까지 허용하는 IOC 지정가를 사용합니다. 미체결 잔량을 남겨 두고 추격하지 않습니다. 일부만 체결되면 실제 체결 수량만 관리합니다.

ATR은 완료된 4시간봉의 최근 14개 true range 평균입니다. 수량과 변동폭을 일관된 단위로 계산하기 위한 것이며, 신호 점수를 만드는 지표가 아닙니다.

Bitget의 실제 타임스탬프로 봉 마감을 계산합니다. 확인한 UTA `1D` 데이터는 UTC 16시(한국 시각 다음 날 01시)부터 시작합니다. 일봉을 임의로 UTC 자정 기준으로 바꾸지 않습니다. 미완료 봉, 봉 사이 누락, 서로 다른 세션 경계는 진입에 사용하지 않습니다.

## 손절과 청산

- 최초 손절은 최근 완료된 4시간봉 3개의 저점/고점과 0.15 ATR 여유폭을 고려합니다. 진입가에서 최소 1.5 ATR, 최소 0.5%는 떨어져야 하며 너무 넓으면 주문을 생략합니다.
- 최초 손절을 진입 주문의 `stopLoss`로 거래소에 함께 전달합니다. 마크 가격 조건의 시장가 손절입니다. 체결 뒤 유효한 거래소 손절이 실제 보유 수량을 덮는지 확인합니다. 확인되지 않으면 본 봇이 연 포지션에 청산을 시도하고 신규 진입을 중지합니다.
- 이후 새 4시간봉이 끝날 때 최근 10봉 저점/고점과 0.15 ATR로 **로컬 손절선**을 조정합니다. 손절을 불리하게 되돌리지 않습니다. 새 구조가 이미 깨졌으면 청산합니다.
- 작은 고정 익절, 가격을 넘어서는 비용 본전 이동, 이익 난 포지션만 시간으로 잘라내는 BAILOUT은 없습니다. 이익을 보유하는 대신 수익을 되돌려 주는 구간도 생깁니다.
- **이 버전은 거래소의 최초 손절을 추세 손절선으로 계속 수정하지 않습니다.** 로컬 손절은 서버가 정상 동작하고 신선한 시세를 받을 때만 작동합니다. 서버가 멈추면 마지막 로컬 수익 보호선이 거래소에 남는 것이 아니라 최초 손절만 남습니다. 재시작 시 현재 가격이 저장된 손절선을 넘었으면 청산을 시도하지만 정지 중 놓친 가격 경로는 복원할 수 없습니다.
- 최초 손절, 로컬 손절, 계좌 손실 한도 모두 시장가 청산의 실제 체결 가격을 보장하지 않습니다.

## 첫 설치와 실매매 시작

ZIP 이름과 압축 내부 최상위 폴더는 각각 `btc_eth_trend_v1.zip`, `btc_eth_trend_v1`입니다. 같은 이름의 기존 설치가 있다면 아래 압축 해제로 덮어쓰지 말고 먼저 상태를 확인하세요.

Windows에서 ZIP을 다운로드 폴더에 저장한 다음 **PowerShell**에서:

```powershell
scp -i "C:\Users\com\Downloads\my-quant-key.pem" "$env:USERPROFILE\Downloads\btc_eth_trend_v1.zip" ubuntu@3.107.6.22:/home/ubuntu/
```

다음은 **EC2 Ubuntu 터미널**에서 순서대로 실행합니다. 앞 명령이 `BLOCKED` 또는 오류를 출력하면 그 원인을 해결한 뒤 계속하세요.

```bash
cd ~
python3 -m zipfile -e btc_eth_trend_v1.zip .
cd ~/btc_eth_trend_v1
bash install.sh
./trend retire-legacy
./trend setup
bash install_service.sh
./trend start-live
./trend status
```

각 단계는 다음 작업을 합니다.

| 명령 | 동작 |
|---|---|
| `install.sh` | Python 버전 확인, 실행 권한 설정, 오프라인 검사. 거래소 접속/거래 없음 |
| `retire-legacy` | 기존 진입 허가 해제, 로컬 상태와 거래소가 모두 비어 있는지 두 번 확인, 같은 프로젝트의 확인된 Larry 실매매 프로세스만 정상 종료 요청. 미청산 포지션이 있으면 종료하지 않음 |
| `setup` | 계좌·봉·상품 단위 검사, BTC·ETH의 교차 5배 설정, 실제 설정 재조회. 매수/매도 주문 없음 |
| `install_service.sh` | systemd 서비스 설치 및 재부팅 시 실행 등록. 즉시 프로세스를 시작하지는 않음 |
| `start-live` | 사전 점검 후 신규 실주문 허용 파일 생성, 관리 프로세스 실행. 조건에 맞는 신호가 생기면 실제 주문 |
| `status` | 실행 여부, 최근 정상 처리 시각, 잔고, 손실 차단, 보유/미확정 주문, 봉 준비 상태 표시 |

서버의 기존 API 키 위치 기본값은 `~/index-sniper-pro/.env`입니다. 키가 그곳에 있다면 추가 입력이 없습니다. 다른 위치를 쓰는 경우에만 설치 폴더에 `connection.json`을 아래 형태로 만듭니다. 이 파일에는 키 자체를 적지 않습니다.

```json
{
  "env": "/home/ubuntu/index-sniper-pro/.env",
  "legacy_root": "/home/ubuntu/index-sniper-pro"
}
```

지원하는 환경변수 이름은 `BITGET_API_KEY`, `BITGET_SECRET_KEY` 또는 `BITGET_API_SECRET`, `BITGET_PASSPHRASE` 또는 `BITGET_API_PASSPHRASE`입니다. UTA 거래·관리 권한이 필요하며 출금 권한이 있는 키는 거부합니다. 키 파일을 채팅으로 보낼 필요가 없습니다.

전용 USDT 계좌/서브계좌를 전제로 합니다. 같은 계좌에서 다른 봇이나 수동 거래를 병행하지 마세요. 주문·포지션을 전체 조회하지만 동시에 움직이는 다른 거래자의 주문까지 원자적으로 잠글 수는 없습니다. 현물 잔고 등 다른 담보의 가격 변동과 입출금은 계좌 손실률 계산에 영향을 줍니다. 입출금을 투자 수익으로 분리하는 현금 흐름 회계 기능은 포함하지 않았습니다.

`retire-legacy`는 확인된 Python 모듈 프로세스만 종료 대상으로 삼습니다. 다른 서비스 관리자가 기존 봇을 자동 재시작하면 새 봇 시작을 차단합니다. 그 경우 기존 서비스의 정확한 이름을 확인해 해당 서비스를 중지해야 합니다. 포지션이 있는 상태에서 강제 종료하거나 데이터베이스를 지우지 마세요.

## 모의 운용과 일상 명령

실계좌 시작 전 공개 시세만 사용하는 모의 운용도 가능합니다.

```bash
./trend doctor-public
./trend start-paper
./trend status --mode paper
./trend report --mode paper
```

모의 운용은 실제 호가 관측을 사용하지만 호가 대기열, 전체 체결 경로, 실제 펀딩 정산을 재현하지 않습니다. 보고서의 `net_before_funding`은 모의 펀딩 전 손익이며 실거래 순수익이 아닙니다. 관측 중 30초 넘는 공백 또는 재시작이 있으면 해당 거래에 `sample_gap`을 표시합니다. 이 결과만으로 수익성이 입증됐다고 판단하지 마세요.

실매매 관리 명령:

```bash
./trend status
./trend report
./trend pause
./trend enable-live
sudo systemctl status btc-eth-trend.service --no-pager
journalctl -u btc-eth-trend.service -n 80 --no-pager
```

`pause`는 신규 진입만 중지하며 기존 포지션의 손절·청산과 미확정 주문 조회는 계속합니다. `enable-live`는 실행 중인 프로세스, 변경되지 않은 코드/설정, 빈 계좌, 손실 한도를 다시 확인한 뒤 신규 진입을 재개합니다. 이미 소비한 신호를 다시 거래하지 않습니다.

기존 포지션/미확정 주문이 저장된 채 프로세스가 멈췄다면 `./trend resume-live`로 **신규 진입을 끈 상태의 복구 실행**을 요청할 수 있습니다. 정상적인 systemd 장애 재시작은 기존 저장 상태를 그대로 이어받습니다. `resume-live`는 이미 프로세스가 실행 중이면 중복 실행을 거부합니다.

봇을 완전히 정지하면 로컬 추세 손절 관리도 정지합니다. 보유 중에는 `pause`를 사용하고 완전 정지는 계좌와 기록이 비어 있는지 확인한 뒤 하세요. 알림은 로컬 로그/systemd journal에 남습니다. 휴대전화 푸시, 텔레그램, 외부 가동 감시 서비스는 이 버전에 포함하지 않았습니다.

최초 봉 수집에는 API 응답 속도에 따라 수 분이 걸릴 수 있습니다. 진입은 4시간봉 마감 직후의 새 돌파만 대상으로 하므로 설치 직후 바로 주문하지 않을 수 있으며, 며칠 동안 관망할 수도 있습니다. 이를 고장으로 생각해 위험 한도를 올리거나 신호를 강제로 만들지 마세요.

## 오류·재시작·기록 처리

- 주문 의도를 SQLite에 먼저 저장한 다음 API를 호출합니다. 타임아웃·응답 유실이면 같은 주문을 재전송하지 않고 `clientOid`로 조회합니다. 해결 전에는 추가 진입을 막습니다. 주문이 계속 조회되지 않는 경우 자동으로 '주문 없음'으로 간주하지 않습니다.
- 체결 내역과 실제 수량을 확인합니다. 본 봇이 열지 않은 포지션은 가져오거나 닫지 않습니다. 다른 거래로 수량이 바뀌면 중지 사유를 남깁니다.
- 단방향 계좌 청산에는 `reduceOnly=yes`, 양방향 계좌 청산에는 기존 `posSide`를 사용합니다. 전체 계좌 일괄 청산 API는 사용하지 않습니다.
- 부분 청산이면 확정된 체결만큼만 남은 수량을 줄이고, 확인된 잔량을 청산합니다. 명시적으로 거부된 청산은 30초 간격으로 최대 3회까지 시도한 뒤 로그에 긴급 점검 필요를 남깁니다. 불명확한 청산 결과에는 자동 재주문하지 않습니다.
- 거래소 포지션 종료 이력의 개설 시각, 원래 수량, 평균 진입 가격을 대조한 뒤 `netProfit`을 순손익으로 기록합니다. 수수료와 펀딩비를 0으로 만들어 수익을 부풀리지 않습니다. 값이 맞지 않거나 종료 기록이 늦으면 다음 거래를 막습니다. 90일 이상 오래된 기록이나 외부 거래가 섞인 이력은 추가 검토가 필요할 수 있습니다.
- `data/live.sqlite`에는 포지션·주문 의도·손실 기준·체결/정산 기록이 있습니다. 재시작·업데이트 시 보존해야 합니다. 미확정 주문 상태를 지워 다시 주문하는 방법은 제공하지 않습니다.
- 새 봇은 자체 단일 프로세스 잠금과 기존 Larry v2의 잠금 파일을 잡습니다. 코드/설정을 수정하면 기존 실주문 허용 해시가 맞지 않아 신규 진입이 중지됩니다. 보유 포지션은 진입 당시 저장된 관리 설정으로 계속 관리합니다.
- `DAILY_LOSS_LIMIT`은 UTC 다음 날, `WEEKLY_LOSS_LIMIT`은 UTC 다음 ISO 주에 다시 평가합니다. `MAX_DRAWDOWN`, `EXCHANGE_STOP_MISSING`, 회계 불일치 등 지속 중지 사유는 단순 재시작으로 지우지 않습니다. 원인과 손실을 확인한 뒤 별도로 처리해야 합니다.

## 검증 범위와 다음 판단

정확한 검사 결과는 `VALIDATION.md`에 있습니다. 현재 패키지는 주문/위험 관리 코드를 검증한 것이며, 여러 시장 국면의 수수료·펀딩·슬리피지를 포함한 독립 구간 수익 검증을 완료한 것이 아닙니다. 앞으로 변경하지 않은 규칙으로 거래를 쌓고, 비용 후 기대값과 최대 손실 폭을 확인해야 합니다. 성적을 보고 과거에 맞게 신호를 계속 바꾸는 방식은 피해야 합니다.

시드의 장기 우상향은 '확률적 우위가 있는 규칙 + 비용 통제 + 제한된 위험 + 지속 검증'이 함께 성립할 때 기대할 수 있습니다. 이 프로그램은 그 검증을 가능하게 하는 한 가지 구현입니다. 수익률, 월 수익, 좋은 집이나 차를 살 수 있는 시점은 약속할 수 없습니다.
