# 1,030 USDT에서 시작하는 자동매매 시스템: A-Z 설계

## 문서 상태

2026-10-13 기준의 제안서입니다. 실제 계좌·저장소 소스·전체 체결 내역을 이번 작업에서 조회하거나 감사하지 않았습니다. 수익을 보장하는 전략이나 완성된 실거래 프로그램이 아닙니다. 함께 제공한 Python 파일은 위험 계산, 기준가 장부, 증액 제안이라는 작은 부분만 구현합니다.

아래 위험 비율과 승급 기준은 처음 검증할 운영 제안값입니다. 실제 백테스트로 최적화되었거나 사용자의 손실 감내 능력이 확인된 숫자가 아닙니다. 생활·이사·대출 상환에 필요한 자금 및 공동 적금과 분리할 수 있는 자금만 프로젝트에 사용합니다.

## A. 목적: 수익과 입금을 분리한다

목표는 1,030달러의 잔고를 단순히 늘리는 것이 아니라, 비용 차감 후 수익성이 있는 규칙을 식별하고 증거에 따라 자금을 배분하는 것입니다. 수익성 미확인, 정상 손실, 실행 오류를 서로 다르게 취급합니다. AI의 역할은 연구와 코드 검증, 사후 분석이며 매 주문의 방향을 자율적으로 바꾸는 역할은 초기 범위에 넣지 않습니다.

## B. 현재 상태부터 인계한다

마지막 공유 기록에 `NATIVE_CHILD_OWNERSHIP_MISMATCH`, 신규 진입 중지 및 BTC 포지션 관련 기록이 있었습니다. 이는 현재 실시간 상태라는 뜻은 아닙니다. 첫 산출물은 거래소 포지션, 일반 주문, 조건부/보호 주문, 실제 체결, 봇 내부 상태를 대조한 인계 보고서입니다. 상태 파일 삭제, 소유권 오류 우회, 무조건적인 전체 주문 취소는 하지 않습니다.

신규 엔진은 우선 읽기 전용입니다. 기존 관리 프로세스를 정지하기 전에 누가 실제 보호 주문을 관리하고 있는지 확인합니다. 관리가 막혀 있거나 보호를 확인할 수 없으면 앱에서 실제 잔여 포지션과 보호 상태를 확인해 처리해야 합니다. 신규 진입 중지만으로 기존 위험이 사라지지는 않습니다.

## D. 거래 범위

초기에는 BTCUSDT·ETHUSDT 선형 USDT 무기한 상품 두 개만 대상으로 합니다. 한 종목에는 한 방향만 보유하고 물타기·마틴게일·피라미딩은 제외합니다. 종목별 거래소 레버리지는 5배 이내, 총 포지션 및 진입 대기 슬롯은 둘 이내입니다. 계정이 hedge mode이면 그 모드에 맞는 주문/청산 계약을 구현합니다. 임의로 one-way로 전환하지 않습니다.

기존 요구였던 종목당 증거금 300 USDT 고정 방식은 이 제안에서는 사용하지 않습니다. 5배 설정은 유지할 수 있지만, 실제 증거금은 구조 보호선과 위험예산에 맞춰 계산합니다. 수량 계산 이유를 알림에 모두 표시합니다.

## E. 위험예산

이는 손실 보장 한도가 아니라 보호 주문이 예상대로 체결된다는 가정 아래 계획한 위험입니다. 실제 체결 이탈, 시장 급변, 거래소 장애, 담보/스테이블코인 위험은 별도입니다. 기존 포지션과 미체결 주문 위험을 동시에 합산하며 롱·숏이라고 상쇄해 주지 않습니다.

종목 명목금액은 E 이내, 합산 명목금액은 1.5E 이내, 단순 추정 초기 증거금 합계는 0.30E 이내로 둡니다. 실제 거래소 필요 증거금·유지증거금·주문 가능한 수량은 별도로 검사합니다. 5배 설정에서 1.5E를 보유하면 단순 초기 증거금은 0.3E라는 산술 관계입니다. 실제 청산 조건을 1/레버리지 하나로 계산해서는 안 됩니다.

## F. 수량 계산

`R = E × 단계별 위험비율 × 낙폭 축소계수`

`d = abs(예상 체결가 - 구조 보호선) / 예상 체결가`

`위험 기준 명목금액 N = R / (d + 비용 여유율 c)`

`실제 N = min(위험 기준 N, 종목 한도, 전체 명목금액 잔여 한도, 증거금 잔여 한도)`

`수량 = 실제 N / 예상 체결가`를 현재 거래소 수량 단위로 내립니다. 최소 주문 미만이면 거래를 건너뛰며, 최소 주문에 맞추려 임의로 올리지 않습니다. stop은 거래소 가격 단위로 먼저 보정하고 그 가격으로 위험을 재계산합니다. 모든 금액은 Decimal 또는 정확한 정수 단위를 사용합니다.

가상 예: E=700, R=3.5, 진입가=80,000, 구조 보호선=78,800, c=0.002라면 이론 N은 약 205.88입니다. 가상 수량 단위 0.0001을 쓰면 0.0025 BTC, 명목금액 200, 5배 단순 증거금 40, 계획 손실+비용 여유 3.4가 됩니다. 실제 시세·실제 수수료·실제 거래소 최소 수량을 뜻하지 않습니다.

비용 c는 진입/청산 수수료, 체결 미끄러짐, 스프레드, 펀딩의 불리한 여유를 포함해 추정하되 같은 항목을 두 번 넣지 않습니다. 수수료 API나 데이터가 누락됐다고 c를 0으로 바꾸지 않습니다. 무기한 보유 시 미래 펀딩 총액은 고정되어 있지 않으므로 c가 전체 손실 상한이 될 수 없습니다.

## H. 첫 연구 가설

수익 가설은 '상위 방향에 맞는 구조 돌파 이후 일부 움직임이 지속되어 거래 비용과 가짜 돌파 손실을 보상한다'입니다. 이는 검증 전 가설입니다. 주봉·일봉은 큰 방향, 4H는 구조, 1H는 필터, 5m는 실행 시점으로 역할을 나눕니다.

비교 출발점의 예는 다음처럼 명확하게 적습니다. 마지막 마감 주봉 종가가 4주 전 마감 종가보다 높고, 마지막 마감 일봉 종가가 20일 전 마감 종가보다 높을 때 롱 방향을 허용합니다. 마지막 마감 4H 종가가 그 봉을 제외한 직전 20개 4H 고가의 최댓값을 넘고, 그 봉의 거래량이 직전 20봉 거래량의 중앙값보다 크면 롱 후보를 냅니다. 숏은 가격 조건을 대칭으로 적용합니다.

이 예의 4주·20일·20봉은 출발용 가설 파라미터이지 검증된 최적값이 아닙니다. 기존 봇의 실제 규칙을 확보하면 그것을 별도의 동결 후보로 유지해야 합니다. 중간에 이름만 같은 전략으로 규칙을 바꾸지 않습니다.

## I. 청산의 객관화

초기 구조 보호선 예시는 신호봉을 제외한 직전 10개 마감 4H 봉의 최저가(롱), 최고가(숏)입니다. 진입 후 새로 마감한 4H 봉을 포함한 최근 10봉 채널로 보호선을 갱신하되 롱은 높아질 때만, 숏은 낮아질 때만 적용합니다. 기존보다 불리하게 보호선을 넓히지 않습니다. 전략 목표가를 고정하지 않고 보호선으로 종료하는 단순 버전부터 시험합니다.

보호선까지 위험을 계산해 놓고 실제 손절은 '4H 종가까지 기다린다'로 다르게 실행하면 위험 계산이 어긋납니다. 보호선에 닿으면 작동하는 거래소 측 보호 방식과 트리거 가격 종류(거래가격/마크가격)를 명시하고 같은 조건을 백테스트에 반영합니다. 서버가 끊겨도 유지되는 보호 주문의 실제 동작을 데모·소액에서 검증해야 합니다.

## J. CCI·CHOP 비교

A: 가격 구조+거래량. B: A에 CHOP 필터만 추가. C: B에 CCI만 추가. 청산, 비용, 자금, 시간 구간을 같게 유지합니다. 지표 수식·길이·임계값·적용 시간대는 실험 전에 문서에 확정하고, 현재 소스 값은 소스를 읽기 전에는 아는 척하지 않습니다. 같은 시간대에서 계산할 충분한 데이터가 없거나 분모가 0이면 해당 필터 신호를 불명으로 처리합니다.

필터가 제거한 손실뿐 아니라 제거한 이익과 거래 수 감소도 측정합니다. 건너뛴 신호를 별도 모의 포트폴리오에서 추적하되, 동시 신호를 전부 실제처럼 합산해 과도한 가상 자본으로 수익을 부풀리지 않습니다. 실제 포트폴리오 비교에는 같은 동시 보유·위험 제약을 적용합니다.

## K. 원본 데이터

Bitget 시장 거래가격 OHLCV, 마크가격, 실제 펀딩 시각과 요율, 상품 수량/가격 단위, 실제 수수료·체결·계좌 변동을 별도로 보관합니다. 원본 응답은 불변 저장, 정규화 데이터에는 해시·수집 버전·조회 범위를 붙입니다. 5m 자료로 1H/4H/일봉을 합성할 때 마감 기준과 결측을 검사하며 주봉 경계도 명시합니다.

현재 공식 문서의 과거 캔들 API는 90일 이전 자료 조회를 안내하지만, 펀딩 이력 API는 최근 90일 제한을 안내합니다. 따라서 3년 가격 자료가 있다고 3년 펀딩까지 갖췄다고 주장할 수 없습니다. 공식 아카이브 등 출처 확인 가능한 자료를 추가 확보하거나, 미확보 기간은 비용 스트레스 가정과 미확보 표시로 평가해야 합니다. 단기 API로 못 가져온 것을 펀딩 0으로 채우면 안 됩니다. 이번 패키지에서는 실제 과거 자료를 수집하지 않았습니다.

## L. 미래 정보 차단

의사결정 시각과 정보가 실제로 이용 가능해진 시각을 따로 기록합니다. 아직 완성되지 않은 주봉/일봉/4H봉의 최종 값, 나중에 확인된 피벗, 미래 뉴스 수정본을 과거 신호에 사용하지 않습니다. 4H 종가 돌파 신호는 그 봉이 마감되고 데이터가 도착한 뒤에만 실행할 수 있습니다. 같은 종가에서 유리하게 체결했다고 가정하지 않습니다.

5m 봉 하나 안에서 진입과 손절이 함께 발생한 상황의 순서를 알 수 없으면 더 작은 시간단위 자료를 쓰거나 보수적 순서를 적용합니다. 미체결 지정가에 가격이 닿았다는 이유만으로 전량 체결 처리하지 않습니다.

## M. 실험 엔진

매매 규칙을 순수 함수로 작성해 백테스트, 실시간 모의, 실제 실행이 같은 함수 결과를 사용하게 합니다. 환경에 따라 달라지는 것은 데이터 입력과 주문 어댑터입니다. 모든 실험은 데이터 해시, 코드 커밋, 파라미터, 비용 모델, 시작 자본, 실험 목적, 결과를 저장합니다. 실패 실험도 지우지 않습니다.

연구 버전과 실전 버전을 분리합니다. 실전은 하나만 계좌에 주문할 수 있습니다. 같은 새 신호를 A/B/C 실전 봇 세 개가 동시에 주문하는 방식은 사용하지 않습니다.

## N. 과최적화 통제

먼저 가설과 후보를 등록하고 시간순 학습/선정/평가를 분리합니다. 여러 시점에서 과거로 선정해 그 다음 구간만 평가하는 전진 검증을 합니다. 과거에 이미 전략 수정에 사용한 기간을 새 '안 본 데이터'라고 부르지 않습니다. 학습·평가 경계를 넘어 보유된 거래가 선정에 미래 성과를 누설하지 않도록 처리해야 합니다.

실험 횟수를 기록하고 수천 조합 중 우승자를 그대로 채택하지 않습니다. 거래를 독립 표본처럼 무작위로 섞는 대신 주간 등 시간 블록과 BTC/ETH의 같은 시점 관계를 유지한 재표본 평가로 불확실성을 점검합니다. 표본이 적으면 '증거 부족'으로 분류합니다.

## O. 평가와 승급

| 평가축 | 확인 항목 |
|---|---|
| 경제성 | 거래 비용 이후 손익, 비용 스트레스 결과, 외부 운영비 이후 프로젝트 손익 |
| 위험 | 미실현 손익 포함 최대 낙폭, 연속 손실, 회복 기간, 꼬리 손실 |
| 견고성 | 종목/기간/국면별 성과, 특정 대형 거래 의존도, 가까운 파라미터 변화 |
| 실행 | 미보호 체결, 중복 주문, 내부/거래소 수량 불일치, 실제와 가상 체결 차이 |

예비 연구 심사 기준으로 평가구간 합산 손익 양수, 이익 합계/손실 절댓값 합계(PF) 1.15 이상, 불리한 비용 2배에서도 손익 양수, 제안 위험 수준에서 낙폭 8% 이내를 둘 수 있습니다. 이는 보장이나 통계적 유의성 기준이 아니라 사전 심사 규칙입니다. 이익을 낸 블록이 하나뿐이거나 수익 추정 범위가 크게 음수를 포함하면 증액 심사는 보류합니다. 통과하는 후보가 없으면 실매매하지 않고 연구를 유지합니다.

30~50건 소액 체결은 실행 문제가 있는지 보기에 쓰는 관찰량 예시일 뿐 수익성 인증이 아닙니다. 3개월 경과 자체도 승급 조건이 아닙니다. 실체결 비용을 반영한 전진 성과와 오류 상태를 함께 검토해야 합니다.

## P. 계좌와 API

전용 운용 계정 또는 검증된 분리 계정에 한 봇만 주문하도록 설계합니다. UTA 설정, 포지션 모드, 종목별 레버리지, 교차/격리, 허용 API 권한, 최소 수량을 실행 전 조회합니다. 숫자가 비어 있거나 비정상이면 해석을 추측해 진행하지 않습니다. 계정/상품 변경을 자동으로 우회하지 않습니다.

읽기 전용 키와 주문용 키를 구분하고 출금 권한은 부여하지 않습니다. IP 제한을 적용하고 키·시크릿·패스프레이즈·텔레그램 토큰을 GitHub/로그/채팅에 넣지 않습니다. 계정 관리 쓰기 권한은 실제 필요 범위를 따져 제한합니다. 공식 문서는 별도 Demo API Key와 데모 접속 방식을 안내합니다. 데모와 실제 키·설정·상태 폴더를 물리적으로 구분합니다.

## Q. 주문 상태 기계

`SIGNAL -> INTENT_SAVED -> SUBMIT_PENDING -> PARTIALLY_FILLED/FILLED -> PROTECTED -> CLOSE_PENDING -> FLAT_RECONCILED`

HTTP 성공이나 주문 ID 발급만으로 체결 처리하지 않습니다. 주문 의도를 로컬에 먼저 영구 저장하고, 매 의도에 고유 clientOid를 부여합니다. 응답 지연 때 새 주문을 다시 보내기 전에 clientOid, 주문 이력, 체결, 포지션을 대조합니다. 거래소의 clientOid 중복 검사 범위만 믿고 영구적인 중복 방지를 생략하지 않습니다.

부분 체결은 실제 체결량만큼 즉시 보호 대상으로 삼고 잔량을 별도로 관리합니다. 보호를 설치/확인할 수 없을 때 남은 진입은 취소하고 확인된 포지션을 모드에 맞춰 정리하는 사전 승인 절차가 필요합니다. 실제 소유권·방향·수량이 불명확한 상황에서 무조건 반대 시장가를 내면 안 됩니다.

## R. 보호 주문의 소유권

로컬 전략 ID, 주문 의도, 거래소 원주문 ID, 네이티브 보호 주문 ID, 트리거 후 파생 주문 ID, 실제 체결 ID의 연결을 보존합니다. 네이티브 파생 주문에 clientOid가 없다는 이유만으로 곧바로 타인 주문이라 단정하지 않고, 공식 응답의 원주문/파생 관계를 확인합니다. 다만 방향·시간·수량이 비슷하다는 이유로 소유권을 추측해서도 안 됩니다.

증명되지 않는 주문은 수동 검토 대상입니다. 신규 진입을 막되 관계없는 주문을 취소하지 않습니다. 보호선 교체는 지원되는 수정 방식과 실제 잔량 점유 규칙을 검사하고, 기존 보호를 먼저 지워 무방비 상태를 만들지 않도록 설계합니다.

## S. 체결 회계와 기준가

실체결 ID로 중복 제거하고 실제 체결가의 손익, 수수료, 펀딩, 리베이트, 강제청산/자동감축, 입출금, 수동 거래를 구분합니다. 이미 체결가에 반영된 슬리피지를 실제 손익에서 한 번 더 빼지 않습니다. 거래소 장부와의 차이는 허용할 근거가 있는 반올림/평가 시점 차이를 제외하고 조사합니다.

함께 구현한 NAV 장부는 체결 원장을 대체하지 않습니다. 검증된 총 평가액과 현금 흐름을 받아 성과를 계산하는 상위 장부입니다. 700 -> 630으로 감소 후 200 입금으로 830이 되어도 수익률은 -10%입니다. `입금 전 기준가 = 입금 직전 평가액 / 기존 좌수`, `추가 좌수 = 입금액 / 입금 전 기준가`로 처리합니다. 출금도 같은 원리입니다.

## T. 추가 납입과 승인 자금

추가 납입액 D는 생활비·이사비·상환·비상자금을 제외하고 본인이 정합니다. 검증 전에는 D를 예비금에 쌓습니다. 손실이나 청산 위험을 메우려고 자동 입금·차입하거나 거래당 위험 비율을 올리지 않습니다.

미해결 사고 없음, 기준가 낙폭 4% 미만, 경제성/실행 검증 통과라는 전제에서 월 1회 사람이 승인합니다.

`다음 승인 한도 = min(이전 승인 한도 × 1.10, 전체 프로젝트 평가액 × 0.70)`

E는 항상 실제 운용 평가액과 승인 한도 중 작은 값입니다. 이익·입금으로 한도가 자동 증가하지 않고 손실은 즉시 E를 줄입니다. 예를 들어 1,030에서 외부로 100을 더 모아 전체 1,130이면, 조건 통과 시 700에서 최대 770으로 확대를 제안합니다. 신규 자금은 다음 진입부터 적용하며 기존 손실 포지션을 추가 매수하는 데 사용하지 않습니다. 감액·이체도 현재 담보와 보유 포지션을 확인한 뒤 시행합니다.

## U. 실시간 관찰

텔레그램은 진입 체결, 청산, 보호 실패, 중단, 재개 승인, 하루 요약 위주로 보냅니다. 빈번한 WAIT는 매번 보내지 않고 일별 통계에 포함합니다. 메시지에는 실제 평가액, 승인 한도, 실제/목표 수량, 계산 근거, 보호 주문 확인 시각, 실현/미실현 손익, 입출금 제외 수익률, 비용, 중단 사유, 전략 버전이 있어야 합니다.

서버 heartbeat와 거래소 상태 정상, 신호 없음, 위험 때문에 거절, 실행 오류 때문에 차단을 서로 다른 상태로 표시합니다. 서버 살아 있음은 보호 주문 정상의 증거가 아닙니다. 서버 외부에서 마지막 heartbeat가 끊겼는지도 확인하는 감시를 별도 설계합니다.

## V. 버전과 배포

기존 GitHub/EC2를 활용하되 저장소와 실제 실행 경로부터 확인합니다. 파일 이름이 같다는 이유로 같은 버전이라 가정하지 않습니다. 커밋 해시·설정 해시·실행 경로·의존성 잠금 파일을 시작 기록에 남깁니다. 운영 상태 데이터는 코드 배포와 분리하고 변경 전 복원 가능한 백업을 만듭니다. 장부 스키마 변경과 되돌리기 호환성을 테스트합니다.

서버에는 주문 권한을 가진 실행자가 하나뿐이어야 합니다. 계정/심볼 범위의 단일 실행 락을 사용하고, 두 번째 서비스가 뜨면 관찰 모드로 거부합니다. 재시작은 자동으로 LIVE 재승인이 아니라 우선 대조 상태로 들어갑니다. 불명확한 기존 포지션을 새 전략의 포지션으로 몰래 편입하지 않습니다.

## W. 장애 시험

응답이 사라졌지만 주문은 성공한 경우, 부분 체결 후 취소, 체결 알림 중복·순서 역전, 보호 주문 생성 실패, 트리거 후 원/파생 ID 변경, 강제 종료 후 재시작, 같은 신호 두 번 처리, 결측 캔들, 시각 어긋남, 소수점 오류, 포지션 0과 미체결 주문 잔존, 수동 청산, 거래 중 입출금을 시험합니다.

합격은 '예외가 안 났다'가 아니라, 중복 포지션이 생기지 않고, 실제 잔여 수량이 일치하고, 보호/청산 담당이 확인되고, 장부 손익이 설명되는 것입니다. 별도의 장애 시험은 아직 이 기초 패키지에 구현되어 있지 않습니다.

## X. 작업 일정

| 순서 | 예상 작업 묶음 | 완료 기준 |
|---|---|---|
| 0 | 기존 상태 대조/인계 | 포지션·보호·장부 불일치 해소 |
| 1주차 | 읽기 전용 수집기, 손익/현금 흐름 장부 | 입금이 수익으로 잡히지 않고 거래소와 일치 |
| 2주차 | 순수 전략 함수와 과거 재생/비용 모델 | 미래 정보·체결 가정 점검 완료 |
| 3~4주차 | 실시간 모의+거래소 데모 주문 시험 | 전략 동결, 오류/체결 경로 검사 |
| 이후 | 조건 충족 시 0.25% 위험 소액 실체결 | 보호·부분 체결·정산 안정성 및 비용 차이 측정 |
| 충분한 전진 기록 후 | 일반 운용/월간 자금 심사 | 경제성·위험·표본·실행 검토 통과 |

기간은 개발 순서의 예시이지 그 날짜가 되면 실매매로 승급한다는 약속이 아닙니다. 일별 짧은 상태 확인, 월요일 성과/비용 검토, 화요일 시험/개발로 시간을 나눌 수 있습니다. 공연 직전 실전 배포는 피하고 검증한 변경만 운영에 반영합니다.

## Y. 비용과 성공의 정의

월 외부 운영비가 가정상 10달러라면 연 120달러로, 초기 전체 1,030 대비 약 11.65%, 운용 700 대비 약 17.14%입니다. 이는 실제 서버 요금 조회가 아니라 비용 부담을 설명하는 계산입니다. 초기 주문 경로에는 유료 LLM 호출을 넣지 않고, 기존 서버의 실제 청구액부터 확인합니다. 공용 서버도 비용을 어떻게 배분했는지 표시합니다.

거래 수익률 0%, 비용 0%라는 가정에서 월 100을 모으면 12개월 뒤 전체 자금은 2,230, 월 200이면 3,430입니다. 이것은 자동매매 예측이 아니라 납입 원금 합계입니다. 프로젝트 성공은 비용 이후 실증된 순수익과 운영 가능한 위험이며, 입금 덕분에 잔고가 커진 것과 구분합니다.

## Z. 다음 구현 완료 조건

실전에 연결하기 전에 기존 소스와 설정(비밀값 제외), 최신 포지션/주문 원본 응답, 체결·재무 기록, 실행 중인 서비스/경로, NATIVE_CHILD 관계를 확보해야 합니다. 이후 실제 계좌에 맞는 어댑터, 데이터 수집, 전략 재생, 회계 대조, 주문/보호 상태 기계, 장애 시험을 차례로 구현합니다.

이 패키지의 첫 실행은 `python3 -m unittest discover -s tests -v` 및 `python3 cli.py demo`입니다. 이는 실거래 승인 명령이 아닙니다. 검증된 수익성이 없다면 자금은 예비금에 남고, 운용 확대는 일어나지 않아야 합니다.
